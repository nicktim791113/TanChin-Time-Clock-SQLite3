文件日期：2026-10-22。對象：接手正式 ERP 的開發人員／ERP agent。

> **狀態：考勤 v1.34.0 API 已實作，隔離測試通過；本機完整測試 313／313 通過。TC-150 尚未安裝此版本，ERP 端仍待修改與驗證。** 本文件是已實作的 API 契約及 ERP 交接說明，不是尚未定義的介面提案。ERP agent 可依本契約開發來源讀取與暫存；正式連線前仍須確認 TC-150 的實際安裝版本及 API 回應，不可將本機實作完成當成正式部署或 ERP 串接完成。

## 1. 要解決的問題與範圍

員工在考勤系統登記想借支的金額，送出後由管理部審核，不經主管審核。管理部可整理每月總表。ERP 主動讀取考勤端借支申請，供管理部核對及後續發放、借支帳與薪資扣回作業使用。

**核准申請不代表已發放款項，也不代表本月應扣薪。** 第一階段的同步應建立可追溯的申請來源資料與待處理清單；不得僅因收到 `approved` 就自動新增已發放借支、登記還款，或修改薪資扣款。

使用者已明確要求：

- 每月 15 日至 20 日讓員工登記；開始日、截止日與金額上限可在活動設定調整。
- 員工自行填寫借支金額並送出。
- 管理部審核；不使用指定主管的請假／加班審核流程。
- 管理者可管理並整理總表。
- 提供 ERP 可讀取的介面。
- 以交接文件及提示詞讓負責 ERP 的 agent 處理 ERP 端，不以本機舊 ERP 副本代替正式版本。

## 4. 考勤 v1.34.0 已實作 API 契約

### 4.1 入口與授權

```text
GET /api/salary-advance-requests
X-API-Key: <由 ERP 既有安全設定取得，不寫入程式碼>
```

讀取權限代碼：`salary_advances`。這是唯讀權限，不授予審核、發放、還款或薪資修改能力。

考勤端新增權限時，須同步檢查舊單一金鑰遷移名單，**不得把新增財務權限自動加入既有 key**。現有 key 須由具權限的人員明確勾選借支讀取權限。

回應採 `{ success, data, meta }` 外層；`data` 是**申請修訂事件陣列**，不是每張申請只出現一次的最新快照。一張單的送出、核准、取消會分別出現，依 `changeSequence` 遞增。ERP 依來源／單號與 revision 更新暫存，不能把每個事件當成另一筆借支。所有請求使用既有來源設定；不得把正式主機位址、金鑰或登入憑證硬編碼進前端。

### 4.2 查詢與同步完整性

v1.34.0 API 支援：

| 查詢欄位 | 用途與限制 |
| --- | --- |
| `applicationMonth` | 登記月份，格式 `YYYY-MM`；不等同於扣薪月份。 |
| `employeeId` | 字串工號；保留前導零。 |
| `cursor` | 非負整數字串，預設 `0`。讀取事件序號大於此值的修訂；成功保存後才更新游標。 |
| `cursorEventId` | 當 cursor 大於 0 時必填，使用上次回應的 `nextCursorEventId`；驗證事件未因資料庫還原而換成其他內容。 |
| `limit` | 1 至 1000 的整數字串，預設 `200`。 |
| `untilCursor` | 第一頁回傳的本次上界；後續分頁帶入同一值，固定本次同步範圍。 |
| `untilEventId` | 明確傳入大於 0 的 untilCursor 時必填，使用第一頁回應的同名值，保護分頁上界。 |

`status` 及 `updatedSince` **不支援**，傳入會回 400。只取核准狀態會漏掉後續撤回／取消，因此介面傳回全部修訂狀態。`meta.hasMore` 為 true 時帶 `cursor=nextCursor`、`cursorEventId=nextCursorEventId`，並沿用原 `untilCursor`／`untilEventId` 讀下一頁；全部成功保存後，以最後一組 nextCursor／nextCursorEventId 作下次起點，並省略舊 untilCursor／untilEventId 讓新事件進入。游標依來源連線及月份／員工篩選條件分開保存，切換篩選不得沿用別組游標。即使本頁無資料，nextCursor 仍可能前進至本次上界，對應事件識別碼也要一起保存。

事件識別碼由考勤端為每次修訂建立不可重用的 UUID。資料庫還原後，即使數字序號重新長到相同值，UUID 仍會不同。游標超過來源上界，或序號與 UUID 檢查點不符時回 409；應核對是否換來源或還原資料庫，不可自行歸零、刪除暫存或重做發放。首次 cursor=0 與完全沒有事件的來源不要求 UUID。API 回傳 400／401／403／409 或 500 時，不更新已成功保存的同步位置。

### 4.3 申請修訂欄位

| 欄位 | 型別 | 意義 |
| --- | --- | --- |
| `sourceSystem` | string | 固定來源種類，例如 `tanchin-time-clock`。 |
| `requestId` | string | 考勤端不可變的申請單號。 |
| `employeeId` | string | 員工工號，例如 `"085"`；ERP 依正式工號欄位對應員工。 |
| `applicationMonth` | string | 登記月份，`YYYY-MM`。 |
| `deductionMonth` | string 或 null | 設定已明確定義時的預計扣回月份；未確認為 null，ERP 不自行推定。 |
| `currency` | string | `TWD`。 |
| `requestedAmount` | integer | 申請金額，新臺幣元。 |
| `approvedAmount` | integer 或 null | 管理部核准金額；未核准為 null，不用 0 代替未知。 |
| `status` | string | `pending_admin`、`approved`、`rejected`、`withdrawn`、`cancelled`。 |
| `revision` | integer | 同一申請每次具業務意義的修改遞增，供重送與衝突判斷。 |
| `changeSequence` | integer | 此次修訂的來源事件序號，供分頁與增量同步。 |
| `changeEventId` | string | 此次修訂的不可重用 UUID，與序號一同識別來源事件。 |
| `createdAt` | string | ISO 8601，含時區。 |
| `submittedAt` | string 或 null | 送出時間。 |
| `reviewedAt` | string 或 null | 管理部審核時間。 |
| `reviewerId` | string 或 null | 審核人識別，不包含登入憑證。 |
| `updatedAt` | string | 最後更新時間，含時區。 |
| `reviewNote` | string | 管理部審核或退回說明；ERP 顯示前應當一般文字處理。 |
| `withdrawnAt`／`withdrawalReason` | string（選用） | 員工撤回時附上，保留來源歷史。 |
| `cancelledAt`／`cancelledBy`／`cancellationReason` | string（選用） | 管理部取消時附上，可能取消原已核准申請。 |

考勤端首版不管理發放，不提供 `paidAmount`／`paidAt`，`meta.paymentRecorded` 固定 false。ERP 不得從 `approvedAmount` 自行補成已發放金額。外部介面不傳申請自由備註、員工姓名／部門及內部活動規則快照；員工顯示資料由既有名冊對應。

ERP 端另保存 `sourceConnectionId`：指向既有考勤來源設定的穩定識別碼，不把可變的主機名稱當成唯一來源鍵。建議唯一鍵為 **`sourceConnectionId + requestId`**；若未來多考勤資料庫共用同一連線設定，須再定義來源實例識別，不能沿用可能重複的單號。

## 5. ERP 應採取的資料流程

1. **讀取申請。** 從 ERP 後端使用既有考勤來源與 API Key 發出唯讀請求；同步人員需要獨立借支資料權限。
2. **保存來源。** 以來源連線與請求 ID upsert 來源紀錄，保存收到的 revision、狀態及同步時間；不要直接覆寫借支帳或薪資列。
3. **核對員工。** 精確比對字串工號；找不到、對應重複或離職等異常列入待處理，不能以姓名猜測或自動改對應。
4. **呈現待處理清單。** 顯示申請月份、申請／核准金額、狀態、來源單號，以及是否已連結 ERP 借支紀錄；尚未確認實際發放者明確標示。
5. **依既有借支流程確認。** 由具權限管理人員核對發放條件與實際發放後，使用 ERP 現有服務建立借支帳，保存來源單號關聯；一張來源申請不得意外重複建立兩筆借支。若允許分次發放，必須另有經確認的拆分規則及累計上限。
6. **依既有還款／薪資流程扣回。** 沿用借支帳 FIFO、月份還款「取代」規則，以及薪資總表借支檢查／預覽後取代 `advanceDeductionAmount` 的作業。不要在同步當下又直接扣一次薪。

借支來源暫存、實際發放借支帳、每月還款、薪資列是不同業務階段。UI 應讓管理部知道目前停在哪一階段，不把「已同步」誤顯示成「已發放」或「已扣薪」。

## 6. 重複同步、更正與撤回

- 同一來源／單號／revision 重送是無變更操作，不新增借支、不累加金額、不重做還款。
- 新 revision 更新來源暫存並保留差異紀錄；較舊 revision 不可覆蓋較新狀態。
- 已核准後更改金額或狀態，若尚未發放，可更新待處理來源；若已連結借支帳／薪資，標示「來源已變更，待人工核對」，不可直接覆寫或刪除財務紀錄。
- 收到撤回／取消／退回仍保留原來源單號與歷史，不做硬刪除。
- 空清單、不完整分頁、API 失敗或來源資料暫時消失，均不能當成「全部取消」。取消必須有明確狀態／事件或事先約定的完整快照規則。
- 一次同步中斷後可重試；同步游標只在資料完整成功保存後推進。跨頁部分失敗要呈現部分完成，不假報全部成功。
- 金額、幣別、工號、月份、狀態或 revision 不合法時拒絕該筆並留可追蹤錯誤，不默默轉 0。
- 已鎖薪資月份只讀；後續來源更正走既有可稽核更正流程，不解鎖、不改鎖定列。

## 7. 權限、個資與操作紀錄

- 員工本人只可看自己的借支申請；指定代辦主管的請假／加班權限不自動取得借支查看或審核權限。
- 管理部申請審核、ERP 同步／檢視、發放確認、還款登記、薪資調整依現有權限分開檢查。
- 真正開發者既有全域稽核、完整資料庫備份與維運權限仍可能接觸借支資料；不將這些既有高階維運權限改成新的財務業務審核權，也不宣稱開發者無法看見任何財務資料。公司須限制高階維運帳號的授權範圍。
- API Key 留在 ERP 後端，不送到瀏覽器、不寫入程式庫／匯出檔／完整請求日誌。
- 來源交換只傳串接所需欄位，不帶卡號、網頁密碼、身分證字號、銀行帳號。
- 操作紀錄至少保存操作者、時間、來源單號、前後狀態／金額、理由、ERP 關聯單號及同步批次；避免記錄驗證標頭。

## 8. 必須驗證的案例

| 案例 | 預期結果 |
| --- | --- |
| 工號 `"085"` | 正確對應，不變成 `85`。 |
| 缺少／無效 key、無借支 scope | 拒絕讀取；不因員工／出勤 scope 放行。 |
| 舊 key 升級 | 不自動獲得新增借支權限。 |
| 同一核准單同步三次 | 一筆來源資料，未發放前不新增借支／扣款。 |
| 同單較新及較舊 revision 交錯 | 最新資料保留，舊資料不倒灌。 |
| 核准但尚未發放 | 只出現在待處理／來源清單，不減少實領薪資。 |

## 附錄 A：同版多段請假的 ERP 相容要求

此項需由接手 ERP 的 agent 一起確認。考勤 v1.34.0 新增一張請假單包含多個不連續日期／時段的能力；一張單仍只有一個申請 ID、同一假別及一套審核流程。**ERP 讀取格式沒有報錯，不代表既有計薪程式已理解新時段。**

### A.1 已由目前考勤程式確認的欄位

來源為 `server.js` 的 `formatLeaveRequestForDashboard`／`formatLeaveRequestForExternal` 及 `leave-date-selection.js`。外部路徑與外層形狀沿用：

- `GET /api/leave-requests`：`{ success: true, data: [申請...] }`。
- `GET /api/leave/requests`：`{ success: true, data: { filters, summary, records: [申請...] } }`。

單筆資料包含：

| 欄位 | 語意 |
| --- | --- |
| `id`／`externalId` | 原請假申請單號，仍為一筆申請；不要每個時段另造一次主管審核。 |
| `employeeNo`／`employeeId` | 字串工號，保留前導零。 |
| `leaveTypeId` | 整張單的假別；各時段沒有另指定不同假別。 |
| `dateSelectionMode` | `legacy_range`、`explicit_dates` 或新增的 `explicit_segments`。原資料欄位 `date_selection_mode` 亦保留。 |
| `leaveSegments` | `explicit_segments` 的精確時段陣列，元素為 `{ id, date, startAt, endAt, hours }`。原資料欄位 `leave_segments` 亦保留。 |
| `leaveSegments[].date` | 該段在 Asia/Taipei 的日期，`YYYY-MM-DD`。 |
| `leaveSegments[].startAt`／`endAt` | Unix 毫秒時間戳；開始含、結束不含。每段在同一臺北日期內，結束可為隔日 00:00。 |
| `leaveSegments[].hours` | 手動核定的實際請假小時，最多兩位小數；不一定等於起訖相減，例如區間內可扣除休息。 |
| `dailyHours` | 按實際日期彙總的每日請假量；`explicit_segments` 應由時段加總核對，不用每日彙總猜測時段。 |
| `start_at`／`end_at` | 外層最早開始及最晚結束的毫秒時間戳，僅為整張單涵蓋範圍。 |
| `startAtIso`／`endAtIso` | 外層範圍的 ISO 時間，不能拿來填滿中間未請假的空檔。 |
| `duration_hours` | 全部實際時段時數合計。 |

### A.2 三種模式分別處理

1. `legacy_range`：沿用既有歷史連續區間解讀與計算方式，不因出現歷史每日分攤資料而擅自轉成選日模式。
2. `explicit_dates`：只計 `dailyHours` 所列的實際選取日及其時數，未選日不計；此模式不提供任意精確時段，不可從每日小時數反推上下午。
3. `explicit_segments`：以 `leaveSegments` 作為日期／時段依據，以每段 `hours` 作為實際請假量，按日期彙總供月結與薪資使用。外層範圍不能替代時段清單。

原本只認得連續期間的 ERP importer、月結帶入、假別統計、缺勤／加班比對或薪資扣款須逐一核對。若不能正確處理 `explicit_segments`，應明確列為待處理並阻止錯誤帶入計薪，不可默默使用外層範圍。不要把未知模式自行當成 legacy_range；模式缺漏的真正歷史資料才依既有相容規則處理。

### A.3 ERP 必測情境

- 週一上午與週五下午同一張單：中間週二至週四不列請假。
- 同一天 09:00–12:00 與 13:00–17:00：兩段合計 7 小時，12:00–13:00 空檔不視為請假。
- 同日其他請假／加班落在兩段間的空檔：以實際時段判斷，不用外層範圍誤判重疊。
- 時段橫跨兩個月份但每段屬於各自日期：各月只取該月實際日期，不按整筆總時數重複入帳。
- 區間 09:00–18:00 填實際 8 小時：使用 8，不用時間差 9 小時取代。
- 原 legacy_range 與 explicit_dates 資料重新同步：計算及歷史扣帳語意維持。
- 同單重送、修正或取消：以原單號及既有版本／更新規則取代來源，不重複計入每日摘要或薪資。
- 已鎖月結／薪資收到改動：保留差異與處理紀錄，不直接覆寫鎖定結果。

交付時需分別說明「借支新接口支援」與「多段請假 consumer 相容」是否完成及正式部署，不將其中一項完成概括成所有 ERP 串接已驗證。
