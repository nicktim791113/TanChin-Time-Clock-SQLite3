# 午餐團膳操作說明

日期：2026-10-01；適用版本：v1.18.0。

v1.20.0 補充：指定主管可以本人個人網頁密碼進員工工作台「主管代辦」→「午餐團膳」，替明確授權的員工填原因代登。主管與員工同樣受截止／結單限制；截止後仍由團膳管理者處理，主管不能更改參加資格、供餐設定、全體餐數或交單。授權可跨部門、多位主管，詳見 `docs/主管代辦操作說明.md`。

第一版在網頁員工／管理者工作台管理午餐預訂，沒有實際領餐、費用結算、薪資連動，也沒有自動傳送訂單到供應商。桌面版啟動同一個 SQLite 與網頁服務，但本次不新增桌面團膳操作頁。

## 第一次啟用

1. 完整管理者以個人網頁密碼登入，選擇「管理者工作台」→「午餐團膳」。
2. 在「供餐制度」填生效日期、每週供餐日、預設最晚變更時間與原因。初始未設定任何供餐星期，不假設週一至週五供餐。所有截止時間固定採台北時間（Asia/Taipei，UTC+8），由伺服器判斷。
3. 同頁設定「全日請假提醒」的工作起訖時間，預填 08:00–17:00，可依公司實際制度調整。僅在一筆已核准請假完整涵蓋此區間、且仍預訂午餐時提示；半日、外出或加班不自動判斷餐點。
4. 在「參加資格」選員工、生效日期、「加入團膳」及原因。參加者從生效日起於供餐日預設用餐，不需每天重新勾選。退出也指定生效日。
5. 日曆選某日，展開「本日供餐／截止時間」，可設定假日供餐、臨時停供、本日截止時間。每日設定優先於每週制度；填寫原因後儲存。

制度與資格採生效日期保存。只能從今天或未來調整，不能改寫過去制度；同一生效日的設定可直接更新，完整前後內容寫入稽核。較晚的已排定制度／資格仍保留並於其生效日套用。

刪除員工或修改人事資料不會偷偷取消訂餐。已刪除但尚有參加資格的人員會在日名單標示「員工已刪除，請處理參加資格」，管理者仍可代登取消或於參加資格選原工號辦理退出，避免無法處理已交單名單。離職／停止參加時請由團膳管理者明確設定退出日期。

## 員工操作

1. 原卡號登入或個人網頁密碼選「員工工作台」後，點「我的午餐團膳」。不需重設帳號或額外 GPS。
2. 月曆可切換月份，日期顯示「用餐／不用餐／未參加／未供餐」，並顯示截止或結單狀態。
3. 點日期，在午餐登記選「不用餐」並儲存；要恢復則改選「用餐」。同一員工同一日始終是一筆登記，沒有額外取消列。
4. 全日請假提醒提供「確認取消餐點」按鈕，確認後直接取消該日預訂。請假核准本身不會取消餐點。
5. 截止前可自由修改；到達截止的那一分鐘或管理者提前結單後，員工不能再自行變更。請聯絡團膳管理者處理。畫面可能尚未刷新，但伺服器仍嚴格檢查截止時間。

員工 API 只回傳本人資料，不提供別人的名單、全體餐數、原因或交單歷史。

## 管理者代登與交單

- 日曆選日期後，日名單最右邊的「代登／修正」可修改用餐與否。管理者異動一律填原因，包含截止後、結單後或過去日期的修正；修正直接更新原筆，稽核包含操作者、時間、原因及修改前後內容。
- 全日請假提醒中的取消按鈕會選取該員工並帶入「不用餐」，管理者填原因再儲存。
- 「目前登記餐數」為現在有效的預訂；「已交給供應商」為最近一次明確交單時保存的份數。兩者不是實際領餐數。
- 實際以電話、紙本或其他管道通知供應商後，填原因並按「結單並記錄交單」，確認日期與份數。可提前結單，結單後員工不可自行變更。
- 結單後修正只會變更目前登記，不會修改既有交單快照。畫面顯示差額、異動人數及名單；即使總餐數相同但人員對調，也會列出異動。
- 重新通知供應商後，按「更新供應商交單」並確認，可保存新版交單快照。舊版留在交單紀錄中，不是重複的取消登記。這不是自動送單。
- 無供餐日不可初次交單；已交單後若臨時停供，可更新為零份交單，保留舊版證據。
- 「匯出月報」下載 CSV，包含供餐、截止、目前與已交單份數、差額、員工預訂及請假提醒。含 UTF-8 BOM、CSV 文字跳脫與試算表公式防護。
- 多人同時操作導致資料版本不同時，日登記與結單會拒絕舊畫面提交，請重新整理後再次確認，不會強制覆蓋新資料。

## 權限

完整管理者及人事管理者模板提供團膳權限。自訂管理者須至少勾選「查看團膳名單、餐數與匯出」，再依職責搭配以下權限：

| 權限 | 範圍 |
| --- | --- |
| `admin.meals.view` | 查看月曆、名單、餐數、交單紀錄、CSV 匯出 |
| `admin.meals.manage` | 加入／退出資格、管理者代登及修正 |
| `admin.meals.settings` | 每週供餐制度、每日供餐與截止時間 |
| `admin.meals.close` | 結單、更新供應商交單 |

資格、制度、代登、結單的 API 也檢查查看權限。系統管理者仍是獨立授權工作台，可授權人員；開發人員需切換本人獲授權的管理者工作台操作，不能把開發角色當成團膳管理 API 的通行證。

## 備份與部署

- 五張新表為 `meal_schedules`、`meal_memberships`、`meal_days`、`meal_choices`、`meal_orders`，均放在原 SQLite，首次啟動自動建立，不搬移實際資料庫到 Git。
- 完整 SQLite 備份／還原包括團膳及交單快照，舊備份可還原並自動補上空團膳表。
- 核心資產備份腳本包含新的後端／瀏覽器模組、測試與文件，營運資料及密碼金鑰仍按既有備份規則限權保管。
- 更新既有服務主機原始碼或安裝新版後須重新啟動軟體／服務，才能使用新 API。GitHub push 不會更新另外一台 `192.168.0.150:3000` 的正在執行服務。
- 發版須參照 `docs/更新紀錄.md`、`docs/快速部署還原說明.md`、`docs/第一次使用系統完整說明書.html` 的備份、版本、測試與部署規則。打包前關閉使用本專案 SQLite 原生模組的測試服務，避免 Windows 檔案鎖定。
